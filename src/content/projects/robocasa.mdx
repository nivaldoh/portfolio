A robot is asked to put a croissant on a cutting board, then fetch a jar of jam from the cabinet and set it beside the croissant. Once the croissant is down, the request changes: put the croissant back on its plate, but still bring the jam. The robot has to undo the part it has finished and keep the part it hasn’t started.

I extended RoboCasa365 so the goal or the scene can change mid-episode without resetting the simulator or the controller, then traced two very different controllers through this change: GR00T N1.5, a vision-language-action policy, and Astra, my harness around a hosted language model that writes Python control programs.

<GoalChange variant="full" wide />

Finishing the original instruction can still be a failure after the goal changes. The evaluation records the croissant and jam requirements separately, so it is possible to see which part of the updated task remains incomplete. Scored on the original task alone, the GR00T episode above would count as a success.

## What I built

I designed the extension, built it on a fork of RoboCasa365 with help from coding agents, and planned and ran the evaluation.

- **A shared simulator wrapper** that blocks resets, checks for a due change after every action, applies it between actions and updates the current task.
- **Records that separate a change from its receipt:** when the change was applied, when it first reached each controller’s input, every requirement, both scores and the stop reason.
- **Two controller interfaces.** GR00T calls the wrapped environment directly; Astra’s programs talk to it over a local socket.
- **Requirement-level scoring** beside RoboCasa’s own success check, so failing to undo the first placement can be told apart from failing to finish the second.
- **Scenario recipes on top of upstream** for three changes: the simulator moves the placed croissant back to its plate, the instruction changes, or the simulator relocates the jam jar. The case study evaluates the first two.
- **Motion primitives for Astra,** adapted from RPent.

<Details summary="When the goal change fires, and how each score is read">

- **Design.** 54 planned episodes: two controllers, nine condition and configuration cells, three repeats per cell. The assignments, their order, the scoring code and the requirement checks were fixed before the first launch.
- **Trigger.** The goal changes once the croissant’s original requirement (on the board, released and settled) has held for ten consecutive actions while the jam’s requirement is not yet met. If that never happens, the episode counts as a no-opportunity episode, not as a response to a changed goal.
- **Original-task score.** RoboCasa’s own BreadSelection success check, evaluated after every action: both objects on the board and the gripper away from the croissant.
- **Current-goal score.** Checks the current destinations with stricter release and settling conditions, and requires both requirements to hold for ten consecutive actions (the ten-sample rule). The returned croissant also requires its original plate to stay in place.
- **Read at the endpoint.** Both scores are read at the end of the episode; an earlier success is never latched. Re-scoring the original goal with the stricter rule agrees with RoboCasa’s check in 52 of 54 episodes.
- **Scene changes** are checked for support, clearance and settling, and must leave the rest of the simulator state unchanged. Actions already queued keep running through a change.
- **Units.** One action is one 20 Hz control step, 0.05 s of simulated time. Every episode allows 1,950 actions (97.5 s), the task’s original horizon.
- **Controls.** No change keeps the original task. Same text re-sends the original wording under a new goal version. From start gives the revised instruction from step 0. Undo, in which the simulator puts the placed croissant back on its plate, ran in one configuration only.

</Details>

<Details summary="What each controller is told and can do">

- **GR00T N1.5** uses the RoboCasa core team’s checkpoint, post-trained on RoboCasa365’s composite-unseen target data, which includes this task. It predicts 16-action chunks, executes each chunk fully and then queries again until the horizon. Its seeds (101–103) are matched across conditions. It is not told that the task may change.
- **Astra** calls a hosted language model at low reasoning effort. Each call returns a Python program segment, which runs in a persistent namespace, or a final answer, which ends the episode. The system prompt warns that the task can change during any action and tells the model to check object state and the success flag. Each episode starts with a fresh context and allows at most 20 model calls. Provider sampling is unseeded.
- **Astra’s primitives**, adapted from RPent: end-effector steps, position servoing, pitch rotation, gripper commands, a scripted top-down grasp and base motion.
- **Privileged state.** Astra sees evaluator feedback and ground-truth poses, so it cannot be credited with independent perception or with recognising completion on its own.

</Details>

## What the evidence covers

The protocol fixed 54 episodes before the first launch, controls included. Twelve were assigned this goal change. In two GR00T episodes the trigger never fired, and one Astra episode was cut short by a model-provider error after the change, leaving nine that finished after a valid change.

<EndpointTable />

This is not a ranking. The controllers differ in training, inputs, change timing, stopping rules and whether they were told the task might change, and Astra reads ground-truth poses and the evaluator’s success flag. With four and five episodes, these counts are not reliability estimates.

In the Astra episode above, the model saw the new goal 340 actions (17 s of simulated time) after it was applied, because the program it had already written kept running. The records do not show that this delay caused the failure.

## Limitations

One task, one kitchen layout and two object configurations that were also used during development, with three repeats per cell. The study does not isolate why either controller failed, whether a longer horizon would help Astra, or whether GR00T can return a croissant it has already placed. The runtime supports one change per episode, each new task needs its own binding of geometry, validity checks and scoring, and the hosted model alias could not be pinned across collection sessions.

## Paper and code

*Teleporting Bread and Changing Goals: Tracing a VLA and a Code-Writing Agent*, single author. Workshop submission (Workshop on Agentic Robotics, CoRL 2026); decision pending. The paper discloses its coding-agent assistance; I checked its reported numbers against the episode records.

The public fork holds the scenario runtime, recipes, motion primitives and the earlier recovery experiments. The controller runners, episode records and analysis scripts behind the paper’s tables are in the paper’s supplement, not in the public branch.
